# Accounts, and why they exist

Security lifecycle: auth events clear the previous account's content and key,
including revoked sessions and direct account switches. Startup also removes
orphaned account caches while retaining guest/local books and import decisions.
`clearBooksKey` invalidates a generation counter synchronously; key operations,
sync work, and store persistence use it to reject work from an ended session.
Key operations additionally check their provider lifetime before installing or
caching a key. Test these boundaries in `securityLifecycle.test.js` and
`SyncContext.test.js` when changing auth or asynchronous persistence.

The server side of the books: the account, the one table behind it, the five gates in front of it, the two ways in, and `localStorage`'s demotion to a cache. The other half of the same story — the build where a household's ledger is a file on their own machine and reaches no server at all — is in `.claude/DESKTOP_APP.md`.

The app was single-user with no auth for its whole life. What ended that is not a second person: it is that **the books moved off the browser**. A Supabase anon key is compiled into the JavaScript bundle and is public by design, so the only thing between a household's ledger and anyone who opens devtools on the deployed app is a row-level-security predicate — and a predicate needs a subject. `auth.uid()` is that subject, which is what makes an account load-bearing rather than a feature.

**One table on the server**, `app_state (user_id, key, value jsonb, updated_at)`: one row per store. `value` is always an encrypted envelope now (`{ v, kid, iv, ct }`) — never the document itself — except for a plaintext row left over from before an account turned encryption on, which hydrate accepts as-is and then resyncs sealed. See `.claude/END_TO_END_ENCRYPTION.md` and the key-design section below for the shape and why it is structured as envelope encryption rather than per-document keys. Not a relational split, because every derivation here loads a whole array and computes over it in JS — so a split buys nothing and costs the synchronous `{ ok, error }` contract that ~40 call sites and the invariant tripwires depend on. One table is also one policy pair to get right instead of fifty.

**Five layers wrap `AppProviders` in `index.js`, in the order the questions have to be answered:**

- **`AuthProvider`** (`src/contexts/AuthContext.js`) — the session and what you can do about it. Mutators return `{ ok, error }` like every store, wrapped in a promise. `status` is a **three-state, not a boolean**: "checking" is real, because a persisted session is read back asynchronously and a gate that read the gap as signed-out would flash the sign-in form at every returning user on every reload. `describeAuthError` is the one place an API string becomes a sentence, so two forms cannot word the same failure differently.
- **`AuthGate`** (`src/components/AuthGate.js`) — **recovery is checked before the session**, because a reset link *signs you in* (that is how the change is authorised) and checking the session first would drop someone who clicked "I forgot my password" onto the dashboard and never ask for a new one.
- **`BooksKeyGate`** (`src/components/BooksKeyGate.js`, behind `BooksKeyContext`) — the books password, set up or unlocked, before anything below reaches for the documents it seals. It sits **above** `SyncProvider`, deliberately: `SyncContext` reads the unwrapped master key through `src/booksKey.js`'s module state, not through a hook, and that key has to exist before there is anything for hydrate to decrypt. Inert — `unlocked` immediately, nothing asked — on exactly the predicate `SyncContext` reads `remote` from, so a local-only or unconfigured build never sees a password screen it has no server to justify.
- **`SyncProvider`** (`src/contexts/SyncContext.js`) — fetches the account's documents in one query, **decrypts each envelope through `booksCrypto.js`'s `decryptDocument`** (a plaintext row, from before encryption, is taken as-is), writes the result into the local cache, and **holds the render until they are there**. Documents are compared through **`canonicalJSON`** (keys sorted), never a bare `JSON.stringify`: Postgres `jsonb` reorders keys, so a plain comparison read every realtime echo of our own write as another device's change, re-applied and re-pushed it, and kept "Saving…" lit forever. The header's sync badge reserves its widest label's width so it cannot reflow the controls beside it. This gate is the load-bearing piece of the whole design: **four** store initialisers (`foldLegacyLedger`, `readStoredLedger`, `legacyPlannedCentsById`, `storedGroupBuckets`) read storage **synchronously** to build their lazy defaults and run before the first paint. Gating the render is what let every migration, every mutator and every tripwire survive the move to Postgres untouched. It also coalesces writes (one round trip per burst of blur-commits, not one per column), **encrypts on the way out** through `flush` (queuing rather than sending if no key is available), keeps a failed push queued rather than dropping it, and subscribes to realtime — which is the `storage` event's job one device wider, since every write replaces a whole document. **Realtime is private Broadcast, never Postgres Changes**: a trigger sends `{ key, op, iv }` to `budget:app_state:<household>` and the client fetches the row it names (skipping the fetch when the `iv` is one it just sealed); `ActivityContext` does the same on `budget:activity:<household>`. Postgres Changes polls and decodes the whole project's WAL for as long as anyone is subscribed, which on this shared project was most of the database's CPU. The receive policies on `realtime.messages` are at the foot of `schema.sql`, and the other app's restrictive boundary must stay scoped to its own topics or it refuses these. `resync()` is the fifth verb: clear `known` and queue every cached document, which is what a still-plaintext account hitting this provider for the first time after setting a books password calls on itself.
- **`ImportBooksGate`** (`src/components/ImportBooksGate.js`) — the one-time offer to carry this browser's pre-account books into an empty account. Offered on **two** conditions, and the second is what makes it safe: this browser holds books *and* the account is still empty, so there is nothing to overwrite. Legacy keys travel too, or a browser that never ran the current build carries up an empty account.

## The key design

**Envelope encryption, not a key per document.** One random 256-bit master key (MK) encrypts every document and every receipt; MK itself is stored only wrapped, under a key derived from the books password and, separately, under a key derived from a printed recovery code. The whole reason to add this one layer of indirection: **changing the books password rewraps 32 bytes and rewrites one row**, never re-encrypts a single document or receipt, so there is no half-rotated state to design around, no transactional RPC, and no window in which some rows are readable under the old password and some under the new. A device already holding MK does not care that another device just changed the password — the password guards the wrap, not the books.

**Two passwords, not one, and the books password is never derived from the account one.** The account password reaches the server on every sign-in (that is what `signInWithPassword` is); a key derived from it would therefore be a key the server could derive too, which defeats the entire point of a key the server never receives. The set-up screen in `BooksKeyGate.js` says this in one sentence, and a password reset only ever touches the account side — it cannot reach the books password, because nothing about it is recoverable by the server at all.

**The local cache stays plaintext**, deliberately, and it is close to forced rather than chosen: `foldLegacyLedger`, `readStoredLedger`, `legacyPlannedCentsById` and `storedGroupBuckets` all read `localStorage` **synchronously** to build a lazy default before the first paint, and `crypto.subtle` is asynchronous — no decrypt could run underneath them without blocking the very thing they exist to avoid blocking on. Encryption therefore covers the **server copy only**; `localStorage` and the desktop books file stay exactly the plain JSON they always were, which is also what keeps the desktop promise that the books are a file a person can open in a text editor.

**Receipts are in scope because `src/receipts.js` is a second, independent door to the server.** `app_state` is reached from exactly one file, confirmed by searching `src/` and `electron/` for `app_state` — but a donation receipt uploaded as a legible PDF beside a sealed row per store would still carry the charity's name, the amount and the date in the clear, which is precisely the content the rest of this change exists to put out of the server's reach. `saveReceipt` seals the bytes under MK in the `ACCOUNT` medium only; the `COMPUTER` and `BROWSER` media are untouched, since those bytes never leave the household's own machine.

**There are two ways in, and the second is not a convenience.** A password is the original route. An emailed credential is the other, and it is here because the project behind these accounts is no longer this app's alone: it also serves another app that signs people in by link, by code and through Google and GitHub, and every one of those routes writes a row in `auth.users` with `encrypted_password` **null**. Such a household has a perfectly good account here and, before this, no way to reach it — `signInWithPassword` answers "invalid login credentials", which the form words as a password that does not match when the truth is that there is no password to match, and password *recovery* was the only way through, which is a strange thing to ask of somebody who never had one. `requestSignInEmail` is that route, and **`shouldCreateUser` is false on it, which is the load-bearing choice**: left at its default this would quietly become a second way to register — one that mints exactly the passwordless account it was written to rescue, and does it for a typo'd address as readily as a real one. An account is created by the sign-up form, which asks for a password and confirms it; this reaches accounts that already exist. Which means an unknown address is refused **by name** (`otp_disabled`), and reporting that refusal would turn the form into a way to test whether a given household keeps their books here — so `isUnknownAccountError` is asked only so the answer can be thrown away: the call reports success either way and the page says "if an account exists", which is true in both cases and distinguishable in neither. It is the same leak the reset form is already worded around.

**One call, two shapes of email, and this is the one place the two builds are offered different *mechanics* rather than different wording.** The browser sends `emailRedirectTo` and follows the link back to its own origin. The shell is served over `app://`, which no mail client and no OS browser can open, so it sends **no** redirect at all — and deliberately not the `app://` origin either, because an un-allow-listed redirect does not fail the request, it falls back to the project's Site URL, and that URL now belongs to whichever of the two apps claimed it, so asking for a link we cannot receive risks sending a household into the *other* app. Saying nothing is the honest version of "the link is not the part you want". The shell reads the six-digit token out of the same email instead, through `verifySignInCode`, under **`type: "email"` and never `"magiclink"`** — both halves are rendered by the project's single Magic Link template, which is why that template has to carry `{{ .Token }}` beside `{{ .ConfirmationURL }}` (see `supabase/schema.sql`'s header, since this is a dashboard setting no SQL can state), but the token in it is an email OTP and verifying it under the link's type is refused. `MAGIC_CODE_LENGTH` is what the copy **says** — six, the project's default — while `checkCode` accepts six to ten digits, because the length is a dashboard setting and insisting on today's value here would turn raising it into a form that refuses every real code. The server is the one that knows; this only catches what obviously is not a code at all.

**`pendingSignInEmail` is half of the credential, not a flag.** `verifyOtp` needs the address as well as the code and only the code was typed, so taking the address from anywhere else would let a code be verified against an address it was never sent to. It is cleared **the moment a session exists**, not when the form is left: this provider outlives `AuthPage`, which unmounts as soon as there is a session and mounts again on the next sign-out, so an address left lying here would greet that sign-out with "check your inbox" for an email sent before the session that has just ended. One sentence covers every way an emailed credential can fail — lapsed, mistyped, or a link followed twice — because a person cannot act on the difference and all three are fixed by asking for another.

**On `AuthPage` this is a second button under the sign-in form, not a mode.** It needs exactly one field and that field is already on the form, so a screen of its own would ask again for the address just typed; the password field sitting above it unused is the honest shape of the choice. It is a `type="button"` so Enter cannot trigger it, and offered on **sign-in only** — there is nothing to email somebody who is registering, and the reset form is already an emailed route. The screen that waits on the email is a fifth state for the recovery form's reason: it is arrived at rather than chosen. Its code field is `type="text"` with `inputMode="numeric"` and `autoComplete="one-time-code"` — the app's no-`type="number"` rule holding for its own reason here, since a code can begin with a zero and is pasted at least as often as it is typed.

**`localStorage` is now a cache with a synchronous read, not the source of truth** — and `src/storage.js` is the only module that knows the shape of a key. Keys are **namespaced by user** (`hb:<uid>:<key>`), and `scopedKey` returns the **bare key when nothing is in scope**. That unscoped mode is not a degenerate path, it is the app's other supported one: an unconfigured build (no `.env.local`) runs signed out on this browser's own books, which is exactly how the whole test suite runs, and the books written before accounts existed *are* the unscoped documents. **Adding a store means adding its key to `STORE_KEYS`** or it lives in the browser and never reaches the server — `storage.test.js` reads the contexts and fails if you forget. Sign-out calls `clearScope`, which is the reason for namespacing at all: the books have to leave the browser with the session.

Two keys are deliberately **absent from `STORE_KEYS`** and present in `clearScope`'s loop beside it instead: `PENDING_SYNC_KEY`, the outbox of writes not yet confirmed, and `BOOKS_KEY_CACHE_KEY` (`src/storage.js`), the device's cached copy of the unwrapped master key (see the key design above). Neither is one of the books — the outbox is a copy of writes already made elsewhere, and the key only opens them — but both hold something that belongs to the session rather than to the browser, so both leave with it on sign-out for the same reason the books do.
