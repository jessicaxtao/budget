# TESTING.md

`CLAUDE.md` carries the environment gotchas, the seeding rules and the five tripwires — the parts that bite on any change. This is the rest: which suite covers what, and why each is shaped the way it is. **Read this before adding a suite, so a new one does not re-test what an existing one already pins down from the right side.**

## Where a test goes

Three shapes, and the choice is not a matter of taste:

- **Props and spies**, where what is under test is a component's own contract — which patch a cell sends, what it does with a refusal. The rows arrive as a prop, so how they got there is somebody else's suite.
- **Through the real providers**, where the claim is that a figure *lands*. Anything crossing a store boundary, any cascade, any modal that writes twice.
- **The pure function, called directly**, where the arithmetic has a rule of its own and React would only be in the way.

A fourth shape is deliberately absent: **nothing mocks a hook.** `DashboardPage.test.js` renders the page through the real providers, and that is what caught a column dropped from the table header and left in its body.

## Props-and-spies suites

`TransactionRegister.test.js` stages `onChange` as a spy, since what it pins down is the cell contract: which patch a cell sends and what it does with the answer. `TransactionsPage.test.js` runs the same edits through the real providers, because an edit is only worth anything if it lands — that is where the direction flip, the refused flip, and the legacy-row correction are checked end to end.

- `SavingsGoalList.test.js` — the row's editing contract: which figure a cell sends, and what it puts back and says when the store refuses one. The store end, the delete cascade and the pool arithmetic are all in `dataModel.test.js`.
- `PaySchedulePanel.test.js` — which fields each cadence asks for and which patch each sends; the store end (the migration from a bare day count, a refused day of the month, the fields a switched-away-from cadence keeps) is in `useDashboard.test.js` with the rest of the paycheck wiring.
- `EmergencyFundPanel.test.js` — `PaySchedulePanel`'s split: which patch each field sends, which fields each answer asks for, and that a refused figure stays on screen with the message beside it.
- `AccountList.test.js` and `CategoryPlanner.test.js` — how the list is divided and what the row's editing contract is, not how the records got there. `CategoryPlanner.test.js` builds its sections with the real `toSections`, because the row reads `effectiveBucket` and a hand-built fixture could supply it differently from the fold the page uses.
- `BalanceHistoryPanel.test.js` — the grid rather than the store: the blank-versus-zero contract, where a typed month becomes an `amountCents` entry, the months around it stay blank ones that clear, and the figure carries forward without a record being invented for it. The store end, including the all-or-nothing window commit, is in `dataModel.test.js`.
- `PayeeField.test.js` — the control's contract: the keyboard, `aria-activedescendant`, Escape not reaching the dialog, and which of the two answers (`onCommit` / `onType`) it reports.
- `CardOfferList` and `CardValueList` — rows and spies, like `SavingsGoalList`; both are driven through `RewardsPage.test.js` rather than alone, since what is worth asserting is the figure the page's own stores produce.

## Pure-function suites

- `paySchedule.test.js` — the calendar arithmetic, and **every date in it is a real day in 2026 written out rather than derived from today**: the weekday is the whole point, so a fixture computed from `todayISO()` would test nothing about a Saturday.
- `rewards.test.js` — its **card offers** and **credits to use up** blocks drive `offerProgress` and `nextOfferWindow` with every date written out against a fixed today, and its **what a card earns** block does the same for the earn rates: that a multiplier and a percentage meet on one figure, that **the household's valuation is what settles which card wins** (asserted both ways round, since that is the claim the comparison rests on), that a card pays its best matching rate and nothing where it claims none, that earnings read the window, the splits, the refunds and the transfers exactly as an offer does, and that a fee year is the year the fee bought.
- `payeeSearch.test.js` — the ranking.
- `assistant.test.js` — the resolution as the pure function it is, with the model's reply written out as an object and every date a real day (2026-10-08 is a Thursday).
- `reorder.test.js` (the subset rule) and `reordering.test.js` (the store end of a drag).
- `chartAxis.test.js` drives only the two functions in that module with a **rule** rather than a shape — `movingAverage`'s null head and `lineRuns`' break across a gap. Everything else there is asserted through the charts, where a tick or a stack is visible as a coordinate; these two matter for *where they refuse to answer*, and a null is invisible in a rendered path.

## Chart suites

`NetWorthChart.test.js` takes props directly — the one pure component worth testing alone — and asserts:

- no coordinate is `NaN`
- an all-zero file draws nothing rather than dividing by an empty domain
- a negative slice is drawn below the baseline, read off the path coordinates, since that is the only place the side is visible
- a decade thins the axis labels rather than printing 120
- focus opens the same read-out as hover
- the hit areas carry a **roving tabindex** — one tab stop, arrows between months — because ten years is 120 of them

`CashflowChart.test.js` is the same suite for the same reasons, plus the one thing that chart can get wrong on its own: a month whose refunds outweighed its spending must draw **above** the baseline, read off the paths against the zero line's own `y1`.

`PlanVsActualChart.test.js` is the third of that family and adds the two rules only it has: the threshold is **on the plot even when every month came in well under it** (read off the dashed line's `y1` against the hit areas' own top), and a month the books do not reach carries **no verdict** while the line still spans it.

`NetWorthByAgeChart.test.js` is `NetWorthChart.test.js`' suite asked of the new chart, and `ScenarioCompareChart.test.js` the same for the comparison lines.

## Page suites, through the real providers

- **`DashboardPage.test.js`** — its **funding against the plan** block checks that no category is judged against its own estimate, that the month budgeted below the plan's total turns the tile and the footing's Budgeted figure yellow with the gap stated, and that a month budgeted up to the plan is not yellow however it is split. Its **move** block drives the figure-as-button on both kinds of row — an overspent one opening already pointed at covering itself, one with money to spare still opening as the destination with the source blank — the before-and-after read-out, the write landing on both rows, and a refused move keeping the form open. Available is the row's first `cell`. Its **drag to reorder** block drives a real drag through dnd-kit's mouse sensor.
- **`NetWorthPage.test.js`** — drives the period stepper, since backfill *is* the stepper plus a modal that writes to the month on screen. Its **settling** block exists for the reason one level up: the claim `FixDriftModal` rests on is that the correction is an *ordinary transaction*, so what has to be asserted is the row that lands in the ledger — whole, `splits` and all — and the gap closing as a consequence of it. Neither is visible to a mocked hook. It also pins down that a hand-valued holding has no gap to settle at all, because growth is not a disagreement about the books.
- **`TransactionsPage.test.js`** — the direction flip, the refused flip, and the legacy-row correction end to end; `SplitParts` through the register and the editor.
- **`ReportsPage.test.js`** — that a refund is netted off its category and not counted as income, that the ranking is the report's own rather than the plan's, that the range moves every figure on the page together, and that an undated record is called out rather than quietly dropped. Its **custom window** block covers the one option that can do what no preset can get wrong: that the two fields appear with the option and bound each other, that the pair is the window, that a window running past this month divides by the months that happened and names both reasons apart, and that a month nobody has lived gets no verdict against the plan while the threshold still spans it.
- **`RetirementPage.test.js`** — runs the *wiring*: that the starting point is the ticked accounts at `useNetWorth`'s values, that seventy percent is seventy percent of the income sources, that a typed figure takes over from a seeded one without the seed leaking back. Its **scenarios** block drives the store through the page: a saved copy does not follow the live plan, using one restores the plan *and* the events, updating overwrites, a clashing name and a fifth scenario are refused, removing one leaves the others their colours, and the sensitivity rows move the way the rates do. It reads what the projection starts the retirement accounts on off the first row of the "Net worth by age" table, and its two shortfall tests seed a household whose budget spends every dollar, since unspent income now builds up in cash.
- **`DonationsPage.test.js`** — what `useGiving.test.js` cannot see: that recording a gift writes the ledger **and** the tag, and that a deduction larger than its gift is refused before *either* write lands. Its **receipt files** block attaches through the hidden file input (`receipt-file-<transactionId>`) and must `waitFor` the stored record, since the write follows an await.
- **`RewardsPage.test.js`** — its card-offer block runs the offer through the real stores: the whole stored record, that only the card's spending in the mapped category counts, a target met with its bonus valued, a credit read as money already paid for and weighed against a fee typed in place, and that "Next round" adds a new record a quarter on and leaves the old one alone. Its **what each card earns** block does the same for rates: the whole stored record from the form, a card's **whole table entered in one pass** and landing as one write, **one bad row refusing all of it** by name and leaving storage empty so the corrected retry cannot double the good rows, the comparison table naming the card to reach for, a valuation typed at the foot of the page changing which card that is, and the per-rate earnings read off the register. **Every query inside a form is scoped to its dialog** (`form(name)`, off `Dialog`'s `aria-label`), because the page holds four modals at once and two of them ask the same questions — and inside the rate form, scoped again to its row's group (`Rate 2`), because every row of it names every category.
- **`PayeeList.test.js`** — goes through the real providers because it reads its own stores and because a rename is only worth anything if every row that names the payee follows it.
- **`AddModals.test.js`** — modal regressions only appear across repeated open/close cycles, so it drives them through a harness that mimics `TransactionsPage`, wrapping `AppProviders` in a `MemoryRouter` because the transaction modal links to `/plan`. Its **assigning income** block drives both of the modal's months: the page's stepper moving an open dialog, and the form's own stepper filing against a month ahead — the title following it, the pool unchanged by stepping forward, the stored record's `period`, the figure named back as already assigned to later months when the form is reopened on this one, and the month returning to the page's own on the next open. The harness's own button is worded "page steps forward" precisely so it cannot be confused with the stepper's "Next month". Its **reminding about card offers** block drives the entry form's reminder through the same stores: silence until the purchase matches, the other card named, the room left after this purchase and the overflow past the cap on the offer's own card, a credit worded as something to use up rather than a rate to earn, and nothing for a date outside the window. Its **naming the card that earns more** block asserts the standing-rate half of that reminder: said only where another card beats the one in hand, and settled by the household's own valuation of a point.
- **`Sortable.test.js`** and `DashboardPage.test.js`' drag block drive a real drag through dnd-kit's mouse sensor.
- **`AskModal.test.js`** — stages the two assistant verbs on `window.__hbDesktop` **without** `resetStorageBackend()`, so the books stay `localStorage`'s and only `isDesktop()` sees the shell, and runs the claim the feature rests on through the real stores: the reading opens a filled-in form and **nothing lands until it is saved**.

## Hook suites, through the real providers

- `useGiving.test.js` — the half worth testing is the half that crosses stores: an untagged outflow is not giving, a tag whose transaction was deleted is gone with it, untagging leaves the money, a deduction is clamped to its gift, a returned gift subtracts, a removed organization keeps its gifts.
- `useEmergencyFund.test.js` — every figure on it crosses a store: that the target counts the essentials estimates and nothing else in the plan, that a typed figure takes over while the derived one is kept, that choosing to type one and typing none is zero rather than a quiet fall back, that what is held is `useNetWorth`'s valuation (a hand-entered statement beating the ledger's own arithmetic), and that an id whose account was deleted is inert.
- `useDashboard.test.js` — the paycheck wiring and the pay-schedule store end.
- `useSpendingReport.test.js` — carries the coverage boundary one level below the page, and is the one place in the suite where a period is **derived from today rather than written out**: what is under test *is* the line between months that have happened and months that have not, which no fixed date can express.
- `useNetWorth.test.js` — sizes a window directly through the numeric `months` option rather than going through a span.

## Infrastructure suites

- **`storage.test.js`** covers the namespacing — that two accounts on one browser cannot read each other's books, that sign-out takes an account's books out of the cache and leaves the unscoped ones alone, and that an empty `[]` is not "books to import". It stages a fake `window.__hbDesktop` and calls `resetStorageBackend()` to pick it up, which is the only reason that export exists — nothing in the app calls it, since the shell cannot change mid-session. Its last test is a tripwire; see `CLAUDE.md`.
- **`useSyncedState.test.js`** is the old `useLocalStorage` suite plus the sync half: what the hook pushes, what it does with a change from another device, and that an unreadable remote document leaves the store alone rather than blanking it. It stages a `SyncContext.Provider` directly rather than standing up a real one.
- **`AuthContext.test.js`** mocks `../supabaseClient` and drives the provider and the gate. Its **signing in by email** block asserts `signInWithOtp`'s `options` **whole**, the discipline this suite keeps for a stored record and for the same reason: those options are the entire security content of the call, so `shouldCreateUser` going missing is exactly the kind of regression nothing else would show as a failure. The two halves worth not losing: an unknown address reports `{ ok: true }` **and** sets `pendingSignInEmail`, since a wording-only fix would leave the following screen distinguishable; and the shell's call carries no `emailRedirectTo` **key at all**, staged by assigning `window.__hbDesktop` the way `storage.test.js` does.
- **`receipts.test.js`** pins the signed-in upload path with a mocked `getSupabase` — it is the bucket's policy.
- **`electronBooks.test.js`, `electronAssist.test.js`, `electronReceipts.test.js`** test main-process code and live in `src/` anyway, the one placement in this suite that contradicts the rest; `CLAUDE.md` has the reason. `electronBooks.test.js` drives `electron/books.js` and pins down durability — the debounce pair, the launch-time backup taken once, the quarantined unreadable file, and that a refused write stays dirty. A mocked `fs` would only assert that the module calls `renameSync`. `electronAssist.test.js` uses `@jest-environment node` and a real HTTP server on a real loopback port standing in for Ollama; what is pinned is the wire — the schema sent as `format` at temperature zero, Ollama's own error passed back, a non-JSON reply refused, and every malformed request refused **before** anything is sent.

## Suites that deliberately do not exist

**`SplitParts` has no suite of its own on purpose**: it holds no rules, only the arithmetic both hosts already exercise. `AddModals.test.js` drives it through the entry form and `TransactionsPage.test.js` through the register and the editor, which is where the two contracts that matter actually live — nothing is written until the whole division checks out, and a refusal leaves the form on what was typed.
