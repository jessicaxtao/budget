# The assistant

The one feature that reads the books with a model, and the one that exists in only one of the two builds. The shell it belongs to is in `.claude/DESKTOP_APP.md`; the forms every reading ends in are in `.claude/UI.md`.

**"Ask" in the header is a sentence read by a model on this computer, and it exists only in the shell.** The model is Ollama at `127.0.0.1:11434`, which the household installs and runs themselves; the host is written into `electron/assist.js` and is **not configurable**, deliberately ignoring `OLLAMA_HOST`, because the desktop build's whole promise is that the books do not leave the machine and a model on somebody else's server would break it in the first sentence anybody typed. In a browser the button is absent rather than present and refusing.

**Asked from main, never from the page, and that is the egress policy's decision rather than a convenience.** Letting the renderer reach loopback would mean a new origin in `guardEgress`, the shell's CSP *and* `vercel.json`, open on every page load whether or not anybody uses this. A request Node makes in the main process is outside Chromium's network stack — `guardEgress` never sees it — so it is made in exactly one place, to exactly one host, and only when somebody has typed a sentence and asked. Two IPC verbs (`assist:status`, `assist:ask`), answered by `ipcMain.handle` since the page awaits them; `assist.ask` refuses an unnamed model, a role it does not know, oversized content and a missing schema **before anything is sent**, because the bridge is the one door out of the sandbox and a verb that would carry anything is a general verb with a narrow name.

**The model reads; it never decides and it never writes.** `src/assistant.js` is a pure module, `payeeSearch.js`' kind, holding both halves that are not the model's. `buildAssistRequest` sends the sentence, the household's names and a JSON schema passed as Ollama's `format`, which Ollama compiles into a grammar so the reply *cannot* be anything but that shape — **the categories and accounts are enums in it**, so a small model is choosing among the household's own names rather than composing them, and an empty list becomes a field that can only be null rather than an empty enum. Payees are not an enum (a new one is a real answer) and go in the prompt instead, most recently used first. `resolveReading` then looks every name up **again** against the live records — `findPayee` (identity, then a search prefix of three or more letters, never a substring), categories and accounts by identity then `searchKey` — so a name the books do not have cannot become an id, and says in `notes` every place the reading and the books did not line up. **Dates are read by `readDatePhrase`, never by the model**: the model passes back the words used ("last friday") and the calendar does the arithmetic, because a model asked what last Friday was will cheerfully answer with a Thursday. A bare weekday is the most recent one *including today*, "last" reaches past today, slashed dates are month-first because `CURRENCY_LOCALE` is en-US, and a date with no year is this year's. With no category named, spending takes the payee's `defaultBudgetId` and then `usualCategory` — the category the household's own ledger files that payee under most often — before anything is guessed; a paycheque never borrows one, since a category on an inflow turns income into a refund.

**Three actions, and each ends in a form the app already has.** `add_transaction` opens `AddTransactionModal` through its `draft` and `notes` props; `move_money` opens `MoveMoneyModal` through its existing `seed` (plus `notes`), with `"To be assigned"` offered to the model as an envelope name and resolved to `TO_BE_ASSIGNED`; anything else is `unknown`, said in the dialog. **The one write made from the dialog itself is a refile** — a payee's spending moved to another category — and it is shown row by row, every row ticked, through `updateTransaction`, the register's own write, plus an optional `updatePayee` default. Only outflows and never a divided receipt: an inflow given a category stops being income, and a division has no single category to move. Both forms open with **nothing written**: the reading is a draft, every field stays editable, submit runs every check, and the store keeps the last word.

**`draft` is applied where the defaults are**, in `AddTransactionModal`'s re-seed effect, with the payee as initial state so `PayeeField` shows it from the first render. Its category waits in `pendingBudgetRef` and is applied by an effect declared *after* the re-seed effect, on the first render its select exists in — a transfer out of the budget only grows a category field once its two accounts are in state, a render after they are seeded. The three forms are mounted only while open inside `QuickEntry`, the header modal's rule, and the resolved object is held in state so the forms' re-seed effects see one stable value.

**Which model is a bare `localStorage` key, `assistModel`, outside `STORE_KEYS`** — `theme`'s reasoning: it is a fact about this computer (which models Ollama has pulled here), not about the books, and through the storage seam it would be pushed to a server whose other devices may not have that model and written into a books file that refuses an unknown key. A stored model that is no longer installed falls back to the first one that is. `SUGGESTED_MODEL` (`qwen2.5:7b`) is the one name the app tells a household to pull.
