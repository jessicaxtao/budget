# CLAUDE.md

Personal budgeting app: Create React App at the repo root, **no backend**, single user, no auth. Every store persists to `localStorage` via `useLocalStorage` (`src/hooks/useLocalStorage.js`) — `useState`-shaped, JSON, optional third `migrate` arg applied to stored values but never to the default.

## Commands

Run from the repo root.

- `npm start` — dev server at http://localhost:3000
- `npm test` — Jest + RTL, watch mode. Single file: `npm test -- --watchAll=false src/App.test.js`
- `npm run build` — production build

No lint script; CRA's ESLint (`react-app`) runs during `npm start` / `npm test`.

## Money and dates

- **Money is an integer number of cents**, always in a `…Cents` field. Never floating-point dollars. Parse input with `toCents` and render with `formatCents` (`src/utils.js`); `toCents` returns `null` for junk, which is how contexts reject bad input instead of writing `NaN`.
- **`toCents` takes a figure written the way figures are written** — "$1,234.56", "1 234.50", a leading sign — because that is how people type money and it is what `formatCents` itself writes, so a field can show its figure as money and hand it straight back. Never reach for `parseFloat`: it reads "1,234.56" as **1**, stopping at the comma and reporting success. Tolerating the punctuation is not tolerating junk — once the symbol, separators and spaces come off, what is left has to be a number and nothing else, so "12 apples" is `null` where `parseFloat` says 12.
- **Rates are an integer number of basis points**, always in a `…Bps` field — same discipline, same reason. `toBps` / `fromBps` / `formatBps` (`src/utils.js`), and `toBps` returns `null` for junk exactly as `toCents` does — and takes a "%" the same way `toCents` takes a "$". A rate stored as `0.025` is a float the retirement projection raises to the power of thirty, so the drift compounds along with the money.
- **Transactions carry a `date`** (`"YYYY-MM-DD"`, local calendar via `todayISO` — never `toISOString`, which is UTC). Periods (`"YYYY-MM"`) are always **derived** with `toPeriod`, never stored, so the two cannot disagree. Legacy records have `date: null` and display as "Undated"; do not backfill invented history.
- **Compare periods with `periodLTE`, never a bare `<=`** — `null <= null` is `true` in JS, which sweeps undated records into sums that already count them. Step months with `addMonths`, never string arithmetic (`"2026-13"` sorts before `"2027-01"`).
- Migrations live next to the store owning the key and are keyed on **field presence** (`"amount" in record`), not a version counter, so they are safe to re-run.

## Routing

`react-router-dom` v6, pinned: v7's `react-router/dom` export cannot be resolved by the Jest resolver in react-scripts 5. Both routers take the shared `routerFuture` flags (`src/routerFuture.js`).

`src/navigation.js` is the single source of truth for pages, feeding both the route table in `App.js` and the tab bar in `AppShell.js` — **adding a page means adding one entry there**. `src/App.js` is only shell; each page owns its state and modals.

Implemented: `/` (dashboard — today's date, this month's headline figures, accounts with their last reconciliation, categories grouped as the plan groups them), `/transactions` (the editable register, a slim to-be-assigned bar, one ledger-entry modal for money in and out, assignment), `/plan` (categories, their estimates and their optional goals, expected income sources, pay schedule, accounts with their opening balances and running totals, and — closed, at the foot — the balance-history grid), `/net-worth` (hero figure and band split, twelve-month stacked chart with a table twin, holdings by band, the monthly update pass). `/retirement` (the outlook — what has to be there against what is on course to be — the year-by-year chart with a table twin, the account picker, and the assumptions). `/reports` (the window's headline figures and bucket split, the month-by-month cashflow chart with a table twin, and spending by category ranked). `/donations` (a year of giving: what was given against what can be claimed, the year's gifts with the organization and the deductible part editable on the row, the goal, and the organizations). `/net-worth` still carries a `Placeholder` for asset allocation, `/retirement` one for scenarios, and `/reports` one listing what is still to come there — a per-category drill-in, a category against its own history, a custom start and end month, a recurring filter, CSV export — and `/donations` one for non-cash gifts, a year against the years before it, pledges, and CSV export.

**The dashboard has no period selector.** It answers "where am I right now" and everything on it is as of `todayISO()`, read once in the page so the date, the countdown and the reconciliation ages cannot disagree. Walking back through the books is the Transactions page's job.

**The two pages cut the same books along different axes, and neither repeats the other.** What each *envelope* holds is a question about the plan, and it is answered once, on the dashboard, by `CategoryLedgerTable`. What actually *happened*, line by line, is the register on `/transactions`. The one envelope figure that survives on the register is what is left to assign — it moves as the ledger is worked through, and the flow it opens has nowhere else to be reached from. A grid of envelope cards on `/transactions` was the old shape of that page; do not put one back.

## State: eight providers in `src/contexts/AppProviders.js`

Add stores there, not in `index.js`. IDs are generated with `uuid` v4 **in the context**, never in form components.

**Provider order is a cascade order** — a store that has to clean up after another's delete sits *outside* it. `TransactionsProvider` and `AssignmentsProvider` wrap `BudgetsProvider` so deleting a category takes its spend and its funding with it; `TransactionsProvider` also wraps `AccountsProvider` so deleting an account can cut its transactions loose; `DonationsProvider` wraps `TransactionsProvider` so deleting an outflow takes the statement that it was a gift with it. Each references the other by id and never reads it back — keep the dependency one-way. **Cross-store maths belongs in a hook, never in a provider** (`useEnvelopes`, `useAccountBalances`, `useGiving`). `UNCATEGORIZED_BUDGET_ID` lives in `src/contexts/constants.js` for that reason.

- **`TransactionsContext`** — `transactions`: **one ledger for every movement of money**, discriminated by `kind` (`TRANSACTION_KINDS.INFLOW` / `OUTFLOW`), never a signed amount. `amountCents` is a non-negative magnitude. **An outflow must name a `budgetId`; an inflow may.** An inflow with no category is income and lands in the pool; an inflow *with* one is a **refund** against that category — a friend's half of dinner, a returned jacket — which goes back into that envelope and never reaches the pool, because the money was already assigned on its way out. Spend $100 on food and be paid back $60 and food shows $40 of activity. `""` from an unpicked select is normalised to `null` at the boundary. **Every new record must name an `accountId`** — refused at the boundary, so the ledger cannot grow half-finished rows. `accountId: null` and the Uncategorized sentinel still *read* fine (legacy records, and the delete cascade), they just cannot be written. Every rule a record has to satisfy is written out once, as the `RULES` list, and checked through `firstBroken` — because two callers check the same rules against different amounts of the record. `addTransaction` builds a whole one and checks all of it. **`updateTransaction` takes a patch and checks only the rules the named fields could break**, which is what lets the register commit one cell at a time and a legacy row — no date, no account — have its description fixed without being asked to invent the rest. It still cannot *open* one of those gaps: clearing a date or an account touches that field, so the rule runs and refuses. The only cross-field rule is "an outflow names a category", and it lists both `kind` and `budgetId` so either side moving re-checks it. A patch that changes nothing is not written, so tabbing across a row does not re-render every consumer once per column. `reassignBudgetTransactions` moves **both kinds**, so a delete cannot strand a refund away from the spend it offsets. `getBudgetTransactions` returns both kinds for the same reason. The lazy default folds the old `income` and `expenses` keys in via `foldLegacyLedger`; the old keys are left in storage. `readStoredLedger` is the no-React read for `AssignmentsContext`'s lazy default. `deleteTransaction` also calls `removeDonation`: a donation record is a statement *about* an outflow and holds no money, so once the outflow is gone there is nothing left for it to describe — a cascade, unlike `detachAccountTransactions`, where what is left is the money and the money still moved.
- **`AssignmentsContext`** — `assignments` per (budget, period): what was **actually put in**. Does *not* carry forward (the balance does). Zero rows pruned; negatives allowed — under rollover that is the only way to pull money back out.
- **`BudgetsContext`** — `budgets` and `groups`, plus one standing `plannedCents` **estimate** per category (the same figure in every period — it describes the category, not a month) and an optional `goalCents` **goal** beside it. The two answer different questions — what a category needs in a month against the balance it is saving towards — and only the goal is nullable: a blank estimate is a category nobody has made their mind up about and reads as zero, while a blank goal is a category not saving towards anything, which is most of them. So they are parsed by different functions: `readGoal` reads "" as `null` (the way a goal is *removed*) and refuses zero, a negative and junk alike, since a bad parse read as null would clear the goal the user was editing. `updateBudget` tells "leave the goal alone" from "take the goal off" through `readGoal`'s `stated`, not through `undefined`. Deleting a budget moves its outflows **and its assignments** onto `UNCATEGORIZED_BUDGET_ID`; dropping the funding instead would ask the user to fund the same purchase twice. Also owns **buckets** (`PLAN_BUCKETS`: essentials / fun / savings). **Every category carries a real one — there is no "ask my group" state.** A group's bucket is only the value a new category *starts* on: `addBudget` resolves it once, at creation, and the record states its own from then on. So moving a category between groups, renaming a group, restating a group's bucket, and `deleteGroup` all leave what a category counts as alone — none of them can move money between the shares of the split as a side effect. `updateBudget` refuses `null` like any other non-bucket. The migration stamps a stored `null` with its group's bucket (read from the `budgetGroups` key by `storedGroupBuckets`), which is what the category was already counting as. `toSections` still hands every row an `effectiveBucket`; it now equals `budget.bucket`, with the section as a fallback only for storage edited by hand.
- **`AccountsContext`** — `accounts` (set up on Configuration, since the list is a standing fact) and `balances` per (account, period) — a statement figure, which **any** account may carry, read only by `useNetWorth` and never by the budget's own maths. `setPeriodBalances({ period, entries })` writes a whole month at once, validating the batch before writing any of it, and `setBalanceHistory({ months })` carries that rule up a level for the backfill grid — a window of months lands in one commit or none, so a year of history cannot end up half written. Both fold through the same `validateBalanceEntries` / `applyPeriodBalances` pair. **A blank amount deletes that row rather than storing zero** — unlike assignments, zero is a real balance here (a card paid off) and "never updated this month" has to stay distinguishable from it. `addAccount`/`updateAccount` validate a name, a type, a scope, an asset class from `ASSET_CLASSES`, and an **opening balance**; a liability stores `UNCLASSIFIED`, since asset class means nothing on a debt. `updateAccount` validates the record **as it would stand after the patch**, so a partial update cannot slip a combination past the checks a whole one gets — and where the patch names `opening` (the form's dollar string) it **drops the stored `openingBalanceCents` before validating**, or the cents already on the record would win validate's `??` and the retyped figure would be taken and silently discarded. **`openingBalanceCents` is signed** — `signedOpeningCents` negates a liability, because the form asks a debt for the amount *owed* as a positive figure; `toStoredBalanceCents` / `toEnteredBalanceCents` are that same conversion exported as a pair, so the two forms that ask for a balance cannot come to disagree about which way a mortgage points. `openingDate` may be `null` (undated, counts from the beginning of the books). **`ACCOUNT_SCOPES` (on-budget / credit-card / off-budget) is an axis of its own, orthogonal to `type`** — a card is a liability spent through and a mortgage one that is only watched, so never treat scope as a subdivision of assets. **Only the off-budget line is load-bearing in the maths**: every derivation asks `spendsThroughBudget` (or its complement `isOffBudget`), which is true of on-budget accounts and cards alike, so a card's opening balance reduces "to be assigned", its balance derives from the ledger, and it is offered in the transaction form. A card is always a liability — `validate` refuses the asset combination, and `AddAccountModal` stops asking the kind question once the card scope is picked. Credit cards get a section of their own on `AccountList` because the total owed is the figure that panel is read for; the maths is unchanged by that split. `scopeLabel` is the shared display name. `DEFAULT_SCOPE` is on-budget, which is also what `migrateAccounts` stamps on a record saved before the field existed — and what an unrecognised scope falls back to everywhere. Deleting an account drops its `balances` but **keeps its transactions**, detaching them. `AccountList` divides by scope first and calls out owned/owed as an inner band only when a section holds **both**, and every row carries **Edit** beside Remove — editing is `AddAccountModal` opened on the record (`account` prop), never typing over the name in the list the way a category is renamed on the plan, because an account is six interlocking answers and a row of inline controls cannot express an answer that removes the question below it. Renaming through delete-and-re-add would take the account's `balances` with it, which is what the edit path exists to avoid. Also carries **`reconciledOn`** — the day the account was last checked against a statement and agreed. Stored, not derived: it is the one fact no ledger can know. `reconcileAccount({ id, date })` is a mutator of its own (defaults to today, `null` clears it) rather than a field on `updateAccount`, because it records something the user *did* rather than restating what the account *is*. A record predating the field reads as never reconciled, not as reconciled today.
- **`IncomePlanContext`** — the paycheques the user *expects*, by cadence. Independent of the ledger in both directions: nothing maps a transaction to the source that predicted it, so neither delete may cascade into the other.
- **`PayScheduleContext`** — one record, `{ cadence, lastPaidOn, periodDays, daysOfMonth }`: the calendar half of the income question, where IncomePlan is the amount half. **The cadence decides which of the other three fields mean anything** (`src/paySchedule.js` owns that mapping), and the ones it does not read are **kept, not cleared** — switching between fortnightly and twice-monthly to see which describes a new job is the point, and a switch that destroys what it switches away from can only be used once. Every field is nullable and independent, because part of a schedule is a real intermediate state and refusing it would blank the field the user just filled in. `cadence` has **no default**: most people are paid every two weeks and the ones who are not are exactly the ones a guess would mislead. A whole-value guard rather than a field-presence migration — the one thing it upgrades is a schedule stored as a bare day count, through `cadenceForDays` (7 → weekly, 14 → fortnightly, anything else → the custom interval), which is also what a `periodDays` set while no cadence is stated names itself. Read through `useNextPaycheck`.
- **`RetirementContext`** — one record, `retirementPlan`: the ages, the rates, and what the plan is counting on. A store of *guesses*, outside the books, and the separation is load-bearing — the projection reads across the stores but nothing flows back, so a scenario moves no money. **Two questions here have two legitimate answers each, and both are stored**: the starting point is either the accounts the user ticks (`accountIds`) or a figure they type (`startingBalanceCents`), and retirement spending is either a share of today's income (`incomeShareBps`, default 7000) or a typed figure (`annualSpendingCents`). A `…Source` field says which is in force and **the other is kept, not cleared** — toggling to compare is the point, and a toggle that destroys what it toggles away from can only be used once. `annualContributionCents` is `null` for "whatever the savings bucket already adds up to". The rates carry real defaults, because unlike an age they have a defensible standing answer: `growthRateBps` 1000 while saving, `drawdownRateBps` 550 once retired, `inflationRateBps` 250. **All three are nominal — before inflation** — which is why the first is ten and not the seven a saver usually quotes: seven is the long-run *real* equity return, already net of inflation, and the projection deflates what it is given rather than assuming it has been deflated already. Entering seven here takes the haircut twice. The pair is set so what comes *out* is roughly the 7% real while saving and 3% real once retired that a planner actually means. **Coherence between fields is *not* checked here** — retiring before you were born is reported by the projection as something it cannot answer yet, because refusing the field the user just typed is the one response that makes a plan uneditable. A whole-value guard rather than a field-presence migration, like `PayScheduleContext`; the key is `retirementPlan`, and the scaffold's `retirementAssumptions` (rates as fractions, a withdrawal rate this plan has no use for) is left in storage unread.
- **`DonationsContext`** — giving, in three keys and **no money**: `donationRecipients` (the organizations), `donations` (one statement per gift), `donationGoals` (one per year). **A donation is not a movement of money, it is a statement about one.** A gift is an ordinary outflow on the register — it leaves an account, comes out of a category, counts against an envelope and appears in the spending report — and the record here is keyed on that transaction's id and carries nothing the ledger already holds: no amount, no date, no account. Copying the amount would give the household two figures for one gift and no way to tell which is the money. `{ transactionId, recipientId, deductibleCents, acknowledged }`. **`deductibleCents` is stated on every gift — there is no "ask the organization" state**, the same rule as a category's bucket: a recipient's `deductible` flag is only what a *new* gift starts on, resolved once at entry, so correcting an organization's status in March cannot restate what a return filed in February claimed. It is also the only form that covers a $200 gala ticket against an $80 dinner. **The one bound this store cannot check is "no more than the gift itself"** — the amount lives on the transaction, which it does not read — so the forms check it where the figure is in hand and `useGiving` clamps what it reads. Deleting an organization **keeps its gifts** and detaches them (`recipientId: null`), the same way spend outlives its category; deleting the transaction removes the tag, and untagging leaves the money alone. `recordDonation` is idempotent on the transaction id — one movement of money is one gift, so recording twice restates rather than duplicates. A goal is `{ year, source, amountCents, shareBps }` with **two legitimate answers and both kept** (`GOAL_SOURCES.AMOUNT` / `INCOME_SHARE`), the `RetirementContext` rule for the same reason: comparing "a tenth of what we earn" against "six thousand" is the point, and a switch that cleared what it switched away from could only be used once. Blank takes a goal off; junk is refused. `ACKNOWLEDGMENT_THRESHOLD_CENTS` (25000) decides nothing — no figure moves because a receipt is missing — it only decides which gifts `useGiving` reports as still needing one.

Mutators that can reject input (`addBudget`, `addTransaction`, `updateTransaction`, `addAccount`, `updateAccount`, `reconcileAccount`, `setAssignedAmount`, `setPeriodAssignments`, `setBalance`, `setPeriodBalances`, `setBalanceHistory`, `setPaySchedule`, `setRetirementPlan`, `addRecipient`, `updateRecipient`, `recordDonation`, `updateDonation`, `setGivingGoal`) return `{ ok, error }`. **Callers must surface the error** — never close a modal as though the write succeeded. Each context memoises its value.

## Envelope budgeting (`src/hooks/useEnvelopes.js`)

One of six hooks that read across stores. `useEnvelopes(period)` returns one row per budget id plus the pool:

```
activity(b, p)  = refunded(b,p) − spent(b,p)          ← signed
available(b, P) = Σ over p ≤ P of [ assigned(b,p) + activity(b,p) ]
carriedIn(b, P) = the same sum over p < P
toBeAssigned(P) = opening(P) + Σ over p ≤ P of [ poolIncome(p) − Σ over b of assigned(b,p) ]
```

**The invariant**, asserted after every mutation by the tripwire in `dataModel.test.js`:

```
toBeAssigned + Σ available === opening + cumulative inflow − cumulative gross spend
```

The assignment terms cancel algebraically, so this checks coverage, not arithmetic. Three conditions keep it true:

1. **`rows` is the union** of budget ids, the Uncategorized sentinel, and every id appearing in the ledger or in `assignments`. Filtering what the *grid* renders is fine; filtering what the *sums* cover is not.
2. **Both sides use the same period filter.**
3. **A refund is counted once on each side, by different routes.** `toBeAssigned` is built from `cumPoolIncomeCents` (uncategorised inflows only) while the identity's right-hand side uses `cumIncomeCents` (every inflow) and a **gross** `cumSpentCents`. Netting refunds off the spend as well would subtract them twice; adding them to the pool as well would create money.

Also:

- **`opening` is the starting balance of the on-budget accounts**, reported separately rather than folded into `cumIncomeCents` — "income in August" is checked against payslips and an account opening is not part of it. Off-budget accounts are excluded: a 401(k) is not grocery money.
- **Rows carry `spentCents` and `refundCents` gross alongside the signed `activityCents`.** Use the signed one wherever the figures have to add up to the balance beside them (the dashboard table); use the gross ones only where the label says "spent" as a quantity.
- **Undated records count in every period's cumulative sums.** On a row they fold into `carriedIn`, never into this month's activity, so the displayed figures add up to the displayed balance.
- **Future-dated records are excluded** until their month arrives — hence the ban on mixing these figures with all-time ones.
- **Rollover is the closed form above**, not a stored carry-in, so past periods are not immutable.
- **The day-one seed** in `AssignmentsContext` opens every category with an assignment equal to its existing spend, so a pre-existing ledger starts at zero envelopes with net cash unassigned. It runs in the **lazy default only**, and reads storage through `readStoredLedger` because no provider is mounted yet.
- **"Fill" tops a category up to its estimate outright**, ignoring carry-in, so sinking funds accumulate.

## Account balances (`src/hooks/useAccountBalances.js`)

The balance-sheet cut of the same ledger: `balance(a, P) = opening(a) + Σ inflows − Σ outflows, through P`. Every dollar appears in both cuts — envelopes say what money is *for*, this says where it *is*.

**Derived, never stored**, which is what separates it from `balances` in `AccountsContext` — that is a hand-entered snapshot, the figure read off a statement. **This hook never reads one**, whatever account it belongs to: what the budget may spend, and what Configuration reports beside each account, is the books' own arithmetic. A snapshot changes what an account is worth on the *net-worth* view and nothing else, which is the seam that keeps the envelope invariant true. Only on-budget accounts are offered in the transaction form, for the same reason as ever.

`accountBalancesAt(accounts, transactions, period)` is the derivation as a plain function; the hook is a `useMemo` over it. **It stays the only definition of what an account holds** — `useNetWorth` runs it once per month across a chart window rather than writing a second one that could drift from the figure shown beside it on Configuration.

## Net worth (`src/hooks/useNetWorth.js`)

The third of the six cross-store hooks, and the join between the app's two ways of knowing what an account holds: the ledger's arithmetic, and the figure the user read off a statement. **Every account can carry both** — a month's snapshot is a record of the whole position, and the everyday accounts are half of it. What differs is the fallback, and the asymmetry is the design:

```
off budget    → snapshot at or before P, else derived   ← carries forward
spent through → snapshot for P exactly,  else derived   ← never carries
```

A 401(k) is worth what the market says, which no ledger can know, so May's figure is the best answer available in June. An everyday account's balance is live arithmetic: a statement read in May is the better answer *for May* — it catches what the books missed, and before the books opened it is the only answer at all — but standing in for June would freeze the account and hide every transaction logged since. So it answers for its own month and hands back. Where both exist, `driftCents` is the difference; it is **reported, never resolved** (that gap is what a reconciliation is for), and `describeSource` is the one place the wording for it lives, shared by `HoldingsTable` and `UpdateBalancesModal` so the two screens cannot describe the same figure differently.

**Snapshots carry forward, never back.** A holding last valued in May is worth May's figure in June and July — which is what makes a once-a-month update enough — but in April it is worth its opening balance. Propagating the earliest figure backwards would draw a flat line across years nobody recorded and present it as history.

**`chartSeries` is `series` with every off-budget holding smoothed between the real snapshots that bracket it, and it exists for exactly one reason: the chart and its table twin.** A holding entered in January and not touched again until June reads, in `series`, as January's figure held flat for four months and then a jump — the true record of what was actually entered, and what `current`, `changes`, `rows`, `tracked` and `driftCents` all need, since whether a holding is stale and what it is worth *right now* are questions about the real snapshots. `chartSeries` answers a different question — the probable shape of the account across the gap. It bridges only real data: before the first snapshot or after the last there is nothing to draw a line to, so the same carry-forward/opening-balance fallback stands, unchanged.

**The line across a gap is bent toward where the money moved, not drawn straight.** An even month-by-month ramp is the right guess for a holding that simply grew — but a lump transfer out of a spending account (a down payment routed through a "Savings" category) makes an even ramp under-credit the holding for however long the gap runs, which reads on the total net-worth line as the money going briefly missing before "catching up": it never left, the account it was already in just hadn't been revalued yet. `indexSavingsSpend` sums, by month, every outflow filed under the **savings** bucket — the one signal available for *when* inside a gap the money likely moved, since this app has no transfer record linking an outflow to the off-budget account it was headed for. `interpolatedOffBudgetCents` weights the ramp by that figure instead of by elapsed months, shared across every off-budget holding rather than attributed to one, because it is a proxy and not a fact. Where a gap holds no savings-bucket spend at all — most of them, where the whole change was market movement — it falls back to the even ramp exactly as before.

`NetWorthPage` is the one place both `series` and `chartSeries` exist side by side: `chartSeries` feeds `NetWorthChart` and its table twin underneath, everything else on the page — `NetWorthSummary`, `HoldingsTable`, `UpdateBalancesModal` — reads the exact figures.

`HOLDING_CLASSES` is a **coarser cut than `ASSET_CLASSES`**: cash / invested / property / debt, mapped by `BAND_BY_ASSET_CLASS` (total — an unmapped class falls to `property`), with any liability going to `debt` whatever it bought. Four bands is where a stacked chart stops being readable, which is also how many hues are validated against each other. `debtCents` is a positive magnitude (matching `owedCents`) with `0` written out rather than negated, since `-0` would travel into every comparison downstream — and `formatCents` normalises it too, because `Intl` renders `-0` as "-$0".

`useNetWorth(period, { months })` returns `series` (oldest first, ending at `period`) and its chart-smoothed twin `chartSeries`, `current`, per-account `rows` (each carrying `valueCents`, the `derivedCents` it would have had from the books alone, and `driftCents`), and `tracked` — **every** account, the list the monthly pass walks, with the month each was **last** updated. That is the account's own latest snapshot and not the one in force at `period`, so stepping back to March does not make a holding updated in August look untouched since February. `needsUpdate` is true only of a hand-valued holding with no figure for the month: an everyday account with none is not waiting on one, it is answered by the books, and flagging it every month would cry wolf.

**The chart is cut by account, not by band.** `buildSlices(accounts)` is the series list — one per off-budget account, plus `SPENDING_SLICE`, a single band holding every account the budget spends through — and each series entry carries `values` keyed the same way. The everyday accounts are working capital passing through rather than holdings, and four of them are four thin bands that change places with each other as the month is spent, so they get one band between them; the account-by-account cut of *those* is the register. Slices are ordered by band and then by the order accounts were added, **never by size**, or the stack reshuffles whenever two holdings cross and the reader reads the reshuffle as movement. `values` is signed and **a slice draws on the side its own figure puts it**, which is what lets the spending band be one series: a month whose cards outweigh its cash is genuinely negative working capital and draws below the baseline. The band totals (`cashCents` … `debtCents`) survive alongside for the summary tiles and `HoldingsTable`, which are the coarse cut.

`changes` is the headline change over each of `CHANGE_RANGES` — 1M, 3M, 6M, YTD, 1Y, 5Y, 10Y, ALL — each carrying `fromPeriod`, `fromCents`, `changeCents` and `changeBps`. **Each entry also carries `months`**, which is what a single entry means both things at once: `from(period, firstPeriod)` names the month the headline measures from, `months(period, firstPeriod)` sizes the chart's window, and picking one range picks both. The two are still allowed to disagree for the same key — "1y"'s window is the twelve columns ending at `period` while its `from` reaches one month earlier, to the month *before* the window opens, because a change "since a year ago" has always measured from outside the window it shares a key with (`netAt` is the fallback that lets it). YTD measures from **December of the previous year**, the close of the old year, not from January's close, and its `months` is the same count the other way — however many months of the year have happened. ALL is the one pair that reads the ledger: both its `from` and its `months` resolve against `firstPeriod` — the earliest month anything is known about the books, an account's stated opening, a snapshot, or a transaction, computed once by `firstKnownPeriod` and returned alongside `changes` — capped at the same **120 months** (`MAX_WINDOW_MONTHS`) `10y` already sits at, for the reason given there. `percentChangeBps` returns `null` for a base of zero or a base on the other side of zero from where the household ended up — −$10,000 to $10,000 is not "up 200%" — and the page prints a dash; the dollar change is always shown, so refusing to invent a percentage costs nothing. Where both are the same side, the denominator is the base's **magnitude**, so a debt shrinking reads as up.

**The Net worth page has a month on it and the dashboard deliberately does not.** Half of what is on it is typed in, and the month it was typed for is the meaning of the figure. The stepper is also the whole backfill mechanism for a *missed month*: step back, `UpdateBalancesModal` writes to the month on screen, step forward. There is no separate mode, because a month entered late is the same record as one entered on time — which is why the modal puts the month in its title.

**Two controls on that page**: the stepper picks the month everything is *as of*, and one `SegmentedControl` (`SPANS`: 3M/6M/YTD/1Y/5Y/10Y/ALL, a subset of `CHANGE_RANGES` filtered by key — 1M is left off, since a one-column chart is not a shape worth drawing) picks how far back both the chart *and* the summary's headline change look. `useNetWorth` takes the picked key as `spanKey` rather than a bare `months` number (though the numeric option still exists and still wins when both are given, which is what lets `useNetWorth.test.js` size a window directly without going through a span at all) and resolves both halves off the one `CHANGE_RANGES` entry, which is what makes this one dial instead of two that could disagree.

**Arriving with years of statements is the other shape of the same job**, and it gets `BalanceHistoryPanel` — a `<details>` closed by default at the foot of Configuration, holding a grid of a year's months × every account, committed through `setBalanceHistory`. Same records, different door: twelve open-and-close cycles of a modal is a chore, and the figures being entered are one series per account, which is a column. It sits on the page with no month in its corner because **every row names its own** — that, not the stepper, is what makes a grid safe there. It reads its own stores rather than taking props, since it needs the accounts, their snapshots and a per-month ledger balance; the last of those comes from `useNetWorth`'s own `series`, never from a second derivation.

**Blank cells are what both forms turn on.** A blank is a month nobody recorded, so what fills it is the fallback for that account — the books for one the budget spends through, the figure above for one valued by hand — shown greyed in the cell so the column reads as the series it is. Seeding a cell with the value it inherits would turn one statement into twelve records of it, which is also why `UpdateBalancesModal` starts a spend-through field **empty** with the ledger's figure beside it: only a typed figure becomes a record, so a monthly pass done on the 12th cannot freeze an account halfway through the month. In the grid, moving the window re-seeds every field, so an unsaved edit is lost — hence the warning beside the stepper while the form is dirty.

## Retirement (`src/hooks/useRetirementProjection.js`)

The fourth cross-store hook, and the only one that reads a store of guesses (the fifth and sixth are `useSpendingReport` and `useGiving`, below). It joins the plan's assumptions to three real figures: the ticked accounts at the value `useNetWorth` gives them (so a holding valued by hand counts at the figure the user entered), the expected income the spending target is a share of, and the savings bucket the contribution defaults to. **Nothing flows back** — no envelope and no balance moves because a scenario was explored.

**Everything is in today's dollars, and that is what makes the comparison honest.** The target is a share of what the household earns *now*, so the balance measured against it has to be in the same money: both rates are deflated once, `real = (1 + nominal) / (1 + inflation) − 1`, and the real rates are reported back so the page can print them beside the ones that were entered. Growing at a nominal 7% and measuring against a today's-dollars target overstates a thirty-year plan by about half, silently — it is the single most flattering error this kind of tool makes.

**Two rates, not one.** Money still being saved is a thirty-year bet; money being lived on is next year's groceries. The accumulation rate stops at the retirement age and the drawdown rate takes over.

```
need(S, n, d) = S × (1 − (1+d)^−n) × (1+d) / d      ← an annuity due
grow(b)       = b × (1+g) + C                        ← while saving
spend(b)      = (b − S) × (1+d)                      ← once retired
```

The withdrawal comes out at the **start** of the year and what is left grows, because that is the order retirement happens in, and `need` is the closed form that matches that recurrence exactly. **The tripwire in `useRetirementProjection.test.js` asserts it**: a balance of `need` on the first day of retirement is a balance of zero on the last. Any change to either half has to keep it green — that is the only thing keeping the closed form and the simulation describing the same plan.

**The series is the answer and the figures are read off it**, so the chart and the headline cannot disagree: `projectedCents` *is* the series' value at the retirement age. Only `need` and `requiredContributionCents` are closed forms, since neither has a simulation to read. Balances are floored at zero — a projection that draws a portfolio below the axis is drawing a debt nobody took on — and the year is called unaffordable only past `SHORTFALL_TOLERANCE` (a dollar), because carrying fractional cents through a sixty-year walk leaves an exactly-funded plan a fraction of a cent short of its final withdrawal, and a headline should not flip on that.

**The Retirement page has no month on it, and that is deliberate in a different way from the dashboard's.** The dashboard is undated because everything on it is as of today; this is undated because nothing on it is about a month at all. A stepper would suggest the projection can be walked back through, and a plan has no history — only a current shape.

## Spending reports (`src/hooks/useSpendingReport.js`)

The fifth cross-store hook, and **the only one whose subject is a span of months rather than an instant** (the sixth, `useGiving`, has a span too, but its unit is the year). Every other view answers a question about one period; a report cannot be, because the whole point of it is that one month is not evidence. Whether a category is overspent is a question about August; whether the estimate against it is *wrong* is a question about the year.

It reads the ledger and `toSections` and **nothing else**. Not assignments — what was put in an envelope is a decision, and a report is about what happened. Not balances, not the openings: money the household already had is not money it earned.

```
netSpent(b) = spent(b) − refunded(b)          ← what the category cost
income      = inflows naming no category
netCents    = income − netSpent = Σ inflows − Σ outflows   ← over the window
```

The store's refund rule carries through unchanged: an inflow **with** a category went back to it, an inflow **without** one is income. That identity is the tripwire in `useSpendingReport.test.js` — both sides count every inflow exactly once by different routes, and netting a refund off spending *and* adding it to income would inflate both halves of the headline at once, which is the one error a savings rate cannot survive.

- **Undated records are in no report.** `useEnvelopes` folds them into every cumulative sum because a balance must account for every dollar; here the axis *is* the month, so placing one would invent the history the migration refused to invent. They are counted instead — `undatedCount` / `undatedSpentCents` / `undatedIncomeCents` — and the page says so, because money missing from a chart has to be visible as missing. Records outside the window, future-dated ones included, simply are not in it: this is a report of a span, not a balance at the end of one.
- **`REPORT_RANGES`** — 3M / 6M / 1Y / YTD / ALL, inclusive of both ends, capped at `MAX_WINDOW_MONTHS` (120, the net-worth chart's ceiling and for the same reason). Only "all" reads the ledger, for the first month on the books. Every path is guarded back to a window of at least the end month, or every per-month figure would divide by an empty list.
- **The per-month average divides by the window, not by the months the category was active in** — that is what amortising *means*, and it is what makes a $1,200 annual premium comparable with the rent beside it. But it stops at the first month on the books (`averagedOverMonths`, `coverageStartPeriod`), or three months of records over a twelve-month window would understate everything fourfold and silently; the page prints the divisor when it differs. Coverage is **global to the window, never per category**, or a category created last month would divide a one-off by one and report it as a monthly rate.
- **Rows are ranked by what was spent, not arranged by the plan.** The plan's order is answered twice already (Configuration sets it, the dashboard reads it); the question here has an order of its own, which is the whole reason a report is worth having. Each row carries its heading, so the arrangement is still readable — it is just no longer the axis. A category with nothing against it is not a row.
- `buckets` is the same three shares `usePlanHealth` reports off the *estimates*, read off the **books** instead — that pair is the comparison. A category filed under no bucket gets a fourth segment rather than being dropped, or the split describes a smaller household than the headline does.
- `shareBps` returns `null` for a whole of zero or a negative one, and the page prints a dash — the same discipline as `percentChangeBps`.

**The page has one control and it sets the span**; everything moves with it together, including the divisor under every per-month figure. There is deliberately no end-month stepper: walking the window back is what the presets already do from the other end, and the window always ends at the current month, so the last column is a month still in progress. **The chart and the table cut the same books along different axes** — the chart is the time axis, the table is the category axis over the whole window — and neither can answer the other's question.

`SpendingByCategoryTable` colours an average above the plan's estimate in `vermilion-ink`. **This is not a second definition of trouble contradicting the envelope view's one rule.** There the rule is `available < 0` and nothing else, because a category carrying money forward can exceed its estimate in one month by design. An average over the whole window removes exactly that defence — there is nowhere left for it to have carried from — so it says the estimate is wrong, which is a statement about the plan rather than about the envelope.

## Giving (`src/hooks/useGiving.js`)

The sixth cross-store hook, and **the only one filed by calendar year**. Everything else here is filed by month, because a month is what a household plans in — but a deduction is claimed on a return, a return covers a year, and a goal that reset every month would be twelve different promises. Hence `YearStepper` beside `PeriodStepper`: same idea, different unit, and neither is a mode of the other. The year comes off each gift's own transaction date (`toYear`), derived and never stored, exactly as a period is.

**The ledger drives the join.** A tag whose transaction is gone contributes to nothing rather than to a figure with no row behind it, which is what makes the cascade in `deleteTransaction` a tidying rather than a correctness fix.

```
given(y)      = Σ tagged outflows dated in y  −  Σ tagged inflows dated in y
deductible(y) = the same sum over min(deductibleCents, amountCents)
```

- **A tagged inflow is money back from the organization and it subtracts** — the ledger's refund rule, applied to the one thing a returned donation changes here: it cannot be claimed in the year it came back. The row is marked `returned` and its deductible cell is not editable, because the sign belongs to the ledger and the way to restate one is to untag it.
- **The deductible portion is clamped to the gift, and the clamp is reported rather than repaired.** An amount edited down on the register leaves the stored figure out of date, not wrong — put the amount back and it means what it said again — so the row carries `statedDeductibleCents` and `clamped` beside the clamped figure.
- **An undated gift is in no year**, the same discipline the spending report applies to months: counted (`undatedCount`, `undatedTotalCents`) and said out loud, because money missing from a total that is going on a return has to be visible as missing.
- **A share-of-income goal is a share of income *recorded*, not expected** — inflows naming no category, the report's own definition — so the target grows through the year, which is what stating a goal that way means. A refund is not income and is not part of what a tenth is a tenth of. `shareOfIncomeBps` is the same figure with no goal involved, and is what most households are actually asking.
- **`byRecipient` lists every organization, including the ones given nothing this year**: it is the list the page manages, not a ranking of the year's activity, and one that vanished in January would read as deleted. Gifts whose organization was removed get one unfiled bucket rather than a row each, because the parts have to add up to the total above them.
- **Nothing here is a tax calculation.** No limits, no carry-forward, no comparison against the standard deduction — those are questions about a whole return, and a figure that looked like an answer to them would be trusted as one.

`DonationList` owns the giving facts and the register owns the money facts: the organization, the deductible part and the receipt are edited on the row (blur for the figure, change for the select, as `TransactionRegister`), while the amount, the date and the description are read-only with a link to the register. **Untagging removes the statement, never the money** — the outflow still happened. `AddDonationModal` writes twice, ledger first, and **checks the giving fields before either write**, so the money is never the write that lands alone; the bound only it can check ("no more than the gift") lives there for the reason above.

## The dashboard (`src/hooks/useDashboard.js`, `src/hooks/useNextPaycheck.js`)

`useDashboard(period)` joins `useEnvelopes` to `toSections` — the envelope figures, arranged the way the plan arranges them. Rows carry `availableCents`, `budgetedCents`, signed `activityCents`, `targetCents` (the standing estimate) and `goalCents` (the balance the category is saving towards, set on Configuration). **`goalCents` is `null` for a category with no goal — which is most of them, and all of the catch-alls** — and `null` renders as a dash rather than as $0. The same rule carries into the subtotals: `sumRows` adds up the goals that exist and returns **`null` when there are none**, so a band with nothing being saved for leaves the column blank instead of reporting a goal of zero. **Every envelope row lands somewhere** — categories under their group, the Uncategorized sentinel and orphans in `otherRows` — which is what lets `totals` be compared against the headline figures. A row is dropped only when all three summed figures are zero.

`CategoryLedgerTable` drives both its header and its body cells off one `COLUMNS` array, so the two cannot disagree about how many columns there are.

`useNextPaycheck(today)` is the join between the stored schedule and `src/paySchedule.js`, which is the calendar arithmetic as a pure module — no React, no colour, no wording beyond the one phrase both readouts share.

**Two families of schedule, and neither is a variation of the other.** An *interval* cadence (weekly, fortnightly, a custom day count) is the closed form `next = lastPaidOn + k × days` for the smallest `k ≥ 1` with `next ≥ today`: at least one period on, so recording today's pay does not point at today, and never in the past, so a schedule nobody has updated in months still names a real date. A *monthdays* cadence (twice a month, monthly) has no payday to step from at all — it is named days of the month, clamped to the month's length, so `31` is the last day whatever the month is. A day count cannot express it: twice-monthly pay is 13 days apart in February and 16 in July, and a "15.2 day" period drifts off the calendar within a quarter.

**A monthdays payday landing on a weekend is paid the Friday before**, which is what nearly every payroll does; bank holidays are not accounted for, so a payday beside one can read a day late. The rule is never applied to the interval family — those are anchored on a real payday, so every step of seven or fourteen days lands on the same weekday it did. Shifting means a month's paydays are **not all inside it** (a payday on the 1st can be paid at the end of the month before), which is why the search window starts a month early and why the candidates are sorted and de-duplicated after shifting rather than before — two days can clamp or shift onto one date, and one payday is one payday.

`describeSchedule` is the single phrase for what a schedule *is* ("every 2 weeks", "on the 15th and the last day"), shared by the dashboard tile and `PaySchedulePanel` so the two cannot describe one schedule differently. On the panel **the cadence comes first and decides what else is asked**, since neither family's fields mean anything under the other; it is also the one control there that commits on change rather than blur, because there is nothing to half-type.

## UI conventions

Tailwind with the Gotham terminal palette and a dense type scale in `tailwind.config.js`. Take new colors from there — **never raw hex or default Tailwind colors**.

**Two surfaces, with text tokens named for the one they sit on.** Dark chrome (`ledger`, `panel`, `panel-raised`, `edge` hairlines) carries `chalk` / `chalk-soft`; the light mint data body inside it (`sheet`, `sheet-alt` zebra, `band` subtotals, `rule` hairlines) carries `ink` / `ink-soft`. Check which surface you are on before picking a token. Accents `azure` (figures, primary action), `verdant` (income, under budget), `vermilion` (expense, over budget), `sulfur` (active tab) are tuned for dark chrome and are too light for text on a light row — destructive actions in the sheet use `vermilion-ink`.

`font-sans` (IBM Plex Sans) for structure, `font-mono` (IBM Plex Mono) for figures, on `text-label` / `text-row` / `text-figure`. Currency goes through `formatCents`; columns of figures get `tabular-nums`, and a large standalone figure does **not** (equal-width digits make a hero number look loose). `formatCompactCents` is the axis-tick form ("$42.5K"), hand-rolled rather than `Intl`'s compact notation so the browser and the test runner cannot disagree. `CURRENCY` and `CURRENCY_LOCALE` are pinned together.

**The four net-worth series colours (`verdant`, `invested`, `property`, `vermilion`) are the one part of the palette chosen by measurement, not by eye** — a stacked chart is read by telling its bands apart. They are validated all-pairs on `panel`: worst normal-vision ΔE 16.3, worst simulated protan/deutan 6.4. That last figure is in the band that is legal **only** with a second, non-colour channel, so `NetWorthChart`'s legend, its direct end-label, and the page's table view are load-bearing accessibility rather than decoration. **Changing one of the four means re-validating all four.**

The chart now draws one series *per account*, and **the number of accounts moves the ramp, never the palette**: colour still says which band, and lightness says which account within it. `styleSlices` steps each band's hue toward the surface by position (`SHADE_FLOOR` 0.5, spread evenly however many are in the band) and same-hue slices are stacked adjacent so each band reads as one ramp. Hue count is what makes a stacked chart unreadable, so a fifth hue is never the answer. The shades are drawn as `fillOpacity` on the band's Tailwind `fill-*` class rather than as mixed hex, which is also why each column gets a `fill-panel` backing rect first — without it the grid hairlines show through a dimmed segment as stripes across the money.

Shared components in `src/components/` — read the file before reusing one. Rules that are not visible from the call site:

- Every page starts with `PageHeader`, whose title is the page's only `<h1>`.
- `Button` `variant` names the surface: `primary` / `outline` / `danger` on dark chrome, `row` and `row-action` inside light data rows. `row` is bare text that turns red on hover — it is what "Remove" wears, and the hover colour is the warning; anything non-destructive takes `row-action`.
- `TallyGauge` treats a non-positive `max` as a zero ratio, so **callers must suppress it rather than pass one**. `SplitGauge` draws nothing at all from all-zero weights, so the same rule applies to it. `RetirementOutlook`'s `FundedMeter` and `GivingSummary`'s `GivenMeter` are the same ticks with the **tone reversed** — full means funded, or the goal met, not spent out — and each is local for exactly that reason: one component reading both ways would be a trap for whichever caller came next, and that is also why the second is not a call to the first.
- `SegmentedControl` and `SourceChoice` look alike and are not interchangeable. `SegmentedControl` is a strip of `aria-pressed` buttons for a choice about **what is on screen** — nothing it does reaches a store, so every option stays in the tab order and comparing them is one click. `SourceChoice` is radios for a question the **plan keeps an answer to**, where the answer not chosen has to stay visible beside it.
- `SourceChoice` is the radio pair for a question with two legitimate answers, used twice on the retirement page and once on `GivingGoalPanel`. **Its two uses must not share an option label** — "a figure I enter" in both groups is two radios with one accessible name between them, so they read as "a balance I enter" and "a yearly figure I enter".
- Help text under a field goes **outside** the `<label>`, tied to the input with `aria-describedby` (see `RetirementAssumptionsPanel`'s `Field`). Nesting it folds a sentence of guidance into the field's accessible name, so nothing can find the field by its name and a screen reader announces the whole paragraph on focus.
- **`src/chartAxis.js` is the arithmetic behind a column chart over months, and it carries no design opinion** — no colour, no layout, no wording, no ARIA. `axisTicks` (which **always includes zero**, guards an empty domain, and rounds to figures people say), `axisLabels` (counted **back from the most recent**, so the right edge is always named), `columnPath`, `stackPaths`, `barWidthFor`, `radiusFor`. `NetWorthChart` and `CashflowChart` both draw through it; what stays in a chart file is what that chart *means* — its frame, its series, and how it says what it is showing. `stackPaths` is the one rule the two share outright: **a value is drawn on the side its own sign puts it**, which is what lets the spending band be one series and a month of net refunds draw upward, and what guarantees the stack's two extents add to the net so the line is always inside the column.
- **A dashed line is for a threshold, never a grid.** The grid hairlines are solid everywhere for that reason; `RetirementChart`'s target line is the one dashed mark in the app, because it is the figure the curve is meant to be measured against.
- Percentages that are shown together go through `apportion` (`src/utils.js`), which splits by largest remainder — three independently rounded shares add to 100 only by luck.
- **No field that takes money is a `type="number"`, anywhere.** A number input refuses "$1,234.56" and "1,234.56" alike — the box looks filled and reads back **empty** — and it renders $78.40 as "78.4", so a column never lines up on its decimal point. Money fields are `type="text"` + `inputMode="decimal"`, and the figure is checked where it always was: at the store boundary, which is why dropping `min` / `step` costs nothing. The same goes for the rate fields, which people write with a "%". Only the ages and the pay-schedule day count are still number fields — a whole number with nothing to punctuate. **The two faces of a money field are `amountAtRest` / `amountEditing`** (`src/utils.js`): formatted at rest, raw under the caret. `amountField` is that pair wired to focus and blur, spread onto fields read back on **submit** — the balance grid, the monthly update, the assign form, which sit beside formatted figures and must not disagree with them. A field that commits on **blur** owns that event and writes its own handler (`TransactionRegister`, `CategoryPlanner`), since what goes back in the box after a refused edit is a question only that field can answer.
- The envelope view has **one** definition of trouble, `available < 0` — not a second rule about the estimate, which an envelope with carry-over can safely exceed.

`Add*Modal` forms are uncontrolled (`useRef` per field, read on submit), stay mounted, and toggle on a `show` prop. **Because they never unmount they must re-seed on open** — a `formRef` effect on `show` that calls `form.reset()`, clears the error, and re-applies defaults. Without it fields keep the previous entry and `<select>` `defaultValue` silently does nothing after first mount. `AssignIncomeModal` recomputes its live counter from `FormData` in one form-level `onChange` rather than holding state per row; its re-seed effect depends on `[show, period]` and deliberately **not** on the rows array. In `AddBudgetModal` the bucket select follows the group select — that is what "the group's default" means now — but only until the user answers it themselves, tracked in a `chosenRef` and reset on open: a choice already made is not a default.

**Three modals add or edit depending on one prop** — `AddGroupModal` (`group`), `AddAccountModal` (`account`) and `AddOrganizationModal` (`organization`) — because each record is a handful of answers that are stated the same way whenever they are stated. What that costs is that the re-seed effect now seeds *from* something, and `seedFor` is where AddAccountModal keeps that in one place: the effect writes the fields through their refs, and the **kind and asset-class selects take the same seed as their `defaultValue`**, mirrored in state. Both unmount whenever a debt or a card is chosen, and a remounted `<select>` takes its `defaultValue` — so a class only written to the DOM comes back as Cash and quietly reclassifies a brokerage. For the same reason `handleChange` falls back to the **account's own** kind rather than the prop default, or a detour through the card option would turn a mortgage into an asset.

`AddTransactionModal` is the one entry point for both directions — money in and money out are one form with a toggle, not two modals. Three things about it are not visible from the call site: the direction is held in **state** (it decides which fields exist, and `form.reset()` cannot reach it, so the re-seed effect sets it explicitly); the form is **replaced entirely** by a pointer to `/plan` when there is no on-budget account or no category, since a form whose submit can only fail is worse than no form (that guard is why the re-seed effect has to tolerate a null `formRef`); and the category select is **keyed on the direction** so switching remounts it, which is what gives each direction its own default — the first category for money out, none for money in. Reusing the element would silently turn the next paycheque into a refund against whatever was picked for the last expense.

`CategoryPlanner` edits four things on the row itself: the **name**, the estimate and the goal are uncontrolled and commit on **blur** (a rejected value — a blank or clashing name, a bad figure — is put back, since the rest of the app still knows the category by the old one), while the bucket select is **controlled**, because there is nothing to type and the choice commits on change. The name input is keyed on the stored name so a successful rename re-seeds it with what was actually saved, and the goal on the stored goal, which has two empty states to tell apart. **The goal cell sends the raw string, not cents** — blank and junk both parse to `null` and only one of them means "no goal", so the store is the one that reads it. Two figure columns on one row is also why the section grew a heading row: with one figure an aria-label was enough. Its unlabelled cells (the drag handle, Remove) are `invisible` copies of the real controls rather than hand-measured widths, and every fixed width — `bucketClass`, `figureClass` — is shared by the heading, the row and the drag overlay so the three cannot drift apart. Both are as narrow as their contents allow, because what they take comes out of the name, which is the only field on the row holding a phrase rather than a short figure.

`TransactionRegister` is the same contract at grid scale, plus four rules of its own. **Money in and money out get a column each**, never one signed figure — that is how a register has always told them apart, and it is also how the direction is *edited*: a figure typed into the other column moves the row across, so a misfiled paycheque costs one edit rather than a delete and a full re-entry. Both amount cells are keyed on the direction **and** the figure, so a commit to either remounts both and nothing is left behind in the column the row came from. **Clearing a cell is an abandoned edit, not a value** — a blank date does not un-date a record and a blank amount is not a transaction of nothing, so both put back what is stored. Amounts are **formatted at rest and raw under the caret**, through `amountAtRest` / `amountEditing` rather than formatting written in the file; `toCents` takes back whatever the field wrote, symbol and separators and all. And the row's current category and account **always have an option**, even one the form would not offer — an off-budget account, a deleted category, the Uncategorized sentinel — or the select would show its first entry and the row would look refiled by being looked at.

Two things about its layout are load-bearing. Cells draw **no rule at rest**, only under the pointer and as an azure box under the caret (the app's global `:focus-visible`): sixty underlines is a grid of noise over the figures the page exists to show, which is why `CategoryPlanner`'s always-on rule does not carry over to a table. And the table is `table-fixed` with a width on every column but Description — **but never a `min-width` on the table**, tempting as one is for narrow windows: Chrome counts a table's min-width against the *document's* scroll width even inside an `overflow-x-auto` box, so a floor wide enough to keep the columns apart puts a scrollbar under the whole page. Keep the fixed widths summing under the container at 768px.

Panels outside a modal that edit a store — `PaySchedulePanel`, `RetirementAssumptionsPanel`, `RetirementStartingPoint`, `GivingGoalPanel` — are uncontrolled too, commit on **blur** (a half-typed "1" on the way to "14" is a valid figure), and key each input on the stored value so a change made elsewhere re-seeds it. A value the store *rejects* changes nothing and so stays on screen to be corrected, with the message beside it. `BalanceHistoryPanel` is the exception that proves the rule: it is a panel, but it commits on **submit**, because a hundred and forty-four cells that each wrote on blur would be a hundred and forty-four writes for one pass over the statements. Its cells are keyed on account, month **and** the figure stored for them, so moving the window and saving both re-seed the grid while typing does neither.

## Testing

- jsdom 16 has no `<dialog>`; `src/setupTests.js` polyfills `showModal` / `show` / `close` and the `close` event. Guarded, so native support wins later.
- Tests seed pre-migration JSON into `localStorage` before `renderHook` and use the real `AppProviders`, exercising migrations and provider order rather than mocking them.
- **Any change to the envelope maths must keep the identity tripwire in `dataModel.test.js` green** — nothing else catches a row-set or cascade regression.
- Seeding the `transactions` key — or the legacy `expenses` key, which still folds in — also fires the day-one assignment seed; to test spend with no funding, write an empty `assignments` key too.
- Any test that writes a transaction must seed an **account** first: the store refuses one without an `accountId`.
- Modal regressions only appear across repeated open/close cycles, so drive them through a harness that mimics `TransactionsPage`. `AddModals.test.js` wraps `AppProviders` in a `MemoryRouter`, because the transaction modal links to `/plan`.
- Tests that assert a whole stored record must list **every** field — `reconciledOn` on an account, `goalCents` on a budget. Three broke when the first was added and three when the second was, which is the point.
- `DashboardPage.test.js` renders the page through the real providers rather than mocking the hooks; it is what caught a column dropped from the table header and left in its body. `NetWorthPage.test.js` does the same and drives the period stepper, since backfill *is* the stepper plus a modal that writes to the month on screen.
- `BalanceHistoryPanel.test.js` takes props too, and drives the grid rather than the store: what it pins down is the blank-versus-zero contract — a typed month becomes an `amountCents` entry, the months around it stay blank ones that clear, and the figure carries forward without a record being invented for it. The store end of that, including the all-or-nothing window commit, is in `dataModel.test.js`.
- `TransactionRegister.test.js` takes props and stages `onChange` as a spy, since what it pins down is the cell contract: which patch a cell sends and what it does with the answer. `TransactionsPage.test.js` runs the same edits through the real providers, because an edit is only worth anything if it lands — that is where the direction flip, the refused flip, and the legacy-row correction are checked end to end.
- `paySchedule.test.js` drives the calendar arithmetic as the pure function it is, and **every date in it is a real day in 2026 written out rather than derived from today** — the weekday is the whole point, so a fixture computed from `todayISO()` would test nothing about a Saturday. `PaySchedulePanel.test.js` takes props and stages `onChange` as a spy, since what it pins down is which fields each cadence asks for and which patch each sends; the store end (the migration from a bare day count, a refused day of the month, the fields a switched-away-from cadence keeps) is in `useDashboard.test.js` with the rest of the paycheck wiring.
- `AccountList.test.js` and `CategoryPlanner.test.js` take props directly, since both take their rows as a prop and hold no state — what they cover is how the list is divided and what the row's editing contract is, not how the records got there. `CategoryPlanner.test.js` builds its sections with the real `toSections`, because the row reads `effectiveBucket` and a hand-built fixture could supply it differently from the fold the page uses.
- **Any change to the retirement maths must keep the tripwire in `useRetirementProjection.test.js` green** — a balance of `need` on the first day of retirement is a balance of zero on the last. It is the only thing holding the closed form and the year-by-year simulation to the same meaning, and everything on the page is a comparison between a figure from one and a figure from the other. The suite drives `projectRetirement` as the pure function it is; `RetirementPage.test.js` runs the *wiring* through the real providers — that the starting point is the ticked accounts at `useNetWorth`'s values, that seventy percent is seventy percent of the income sources, that a typed figure takes over from a seeded one without the seed leaking back.
- A `<dt>` does not take its accessible name from its content, so `getByRole("term", { name })` finds nothing. Reach a figure through its term's text and `nextElementSibling`, scoped to the region — most of these labels deliberately also name the input that sets them.
- A `type="number"` input in jsdom refuses non-numeric text exactly as a browser does, so junk never reaches the store from one — but the only number fields left are the ages and the day count. Money and rates are textboxes, so `getByRole` wants **`"textbox"`**, `toHaveValue` takes a **string** ("$12,500", or `""` for empty, never `null`), and a rejected figure can be tested with a word again.
- `NetWorthChart.test.js` takes props directly — it is the one pure component worth testing alone, and what it asserts is that no coordinate is `NaN`, that an all-zero file draws nothing rather than dividing by an empty domain, that a negative slice is drawn below the baseline (read off the path coordinates, since that is the only place the side is visible), that a decade thins the axis labels rather than printing 120, and that focus opens the same read-out as hover. React 17+ delegates `onFocus` through `focusin`, so use `fireEvent.focusIn`, not `fireEvent.focus`. The hit areas carry a **roving tabindex** — one tab stop, arrows between months — because ten years is 120 of them.
- `CashflowChart.test.js` is the same suite for the same reasons, plus the one thing that chart can get wrong on its own: a month whose refunds outweighed its spending must draw **above** the baseline, read off the paths against the zero line's own `y1`, since the side is only visible in the coordinates. `ReportsPage.test.js` runs the wiring through the real providers — that a refund is netted off its category and not counted as income, that the ranking is the report's own rather than the plan's, that the range moves every figure on the page together, and that an undated record is called out rather than quietly dropped.
- `useGiving.test.js` drives the join through the real providers, because the half worth testing is the half that crosses stores: an untagged outflow is not giving, a tag whose transaction was deleted is gone with it, untagging leaves the money, a deduction is clamped to its gift, a returned gift subtracts, a removed organization keeps its gifts. `DonationsPage.test.js` covers what the hook cannot see — that recording a gift writes the ledger **and** the tag, and that a deduction larger than its gift is refused before *either* write lands.
- **Any change to the report maths must keep the identity tripwire in `useSpendingReport.test.js` green** — `netCents` equals every inflow less every outflow in the window, computed straight off the seed with no notion of income or refunds in it.
